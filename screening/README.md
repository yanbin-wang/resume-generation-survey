## 一、核心结论

1. **筛选是招聘技术里研究最密集的方向之一**：已形成传统 NLP+ML、LLM/生成式、效度审计三条路线，且多为正式 IEEE 会议论文而非预印本，证据强度高于生成侧。

2. **传统方法仍是多数 ATS 产品的实际内核**：TF-IDF + 余弦相似度 + NER 的排序方案、XGBoost 分类（77%）+ 自定义 NER 的两段式，确定性强、可解释、成本低。

3. **LLM 路线关注「公平 + 可解释」**：ChatGPT-4o 框架做三件事——JD 技能加权、结合 GitHub/LinkedIn 公开资料、匿名化敏感属性，最后给出可解释的排序理由。

4. **LLM 筛选的可靠性本身是开放问题**：普林斯顿团队在 AAAI IASEAI 的效度审计发现，多个模型无法稳定选出更合格候选人，资历相当时不会可靠「弃权」，不同人群选择率存在差异。任何把 LLM 排序当决策依据的产品，必须先回答这类审计问题。

## 二、三条技术路线

### 2.1 传统 NLP + 机器学习

用 TF-IDF、余弦相似度、命名实体识别（NER）或分类器完成简历与 JD 的匹配排序，是积累最厚的部分。

- 有 IEEE 会议论文用 **TF-IDF + 余弦 + NER** 做简历排序，除性能外还讨论偏见、透明度与数据隐私——说明「可解释与合规」从传统方法时期就是固定议题。
- 有工作用 **XGBoost 做职位分类（准确率 77%）**，配合自定义 NER 完成信息抽取，属「先抽取结构化字段、再分类匹配」的典型两段式。
- 也有综述系统梳理 TF-IDF、余弦相似度、NER 及协同过滤等排序技术，可作入门地图。

工程含义：这类方法确定性好、可解释、成本低，至今仍是多数 ATS 产品的内核——生成侧那些「31 项规则检查」，本质与之一脉相承。

### 2.2 LLM / 生成式 AI

一篇 IEEE 论文提出用 **ChatGPT-4o 构建「公平且可扩展」的筛选框架**，三点值得注意：

1. 从 JD 提取技能并**加权**，而不是所有关键词等权匹配；
2. 分析简历时**结合 GitHub / LinkedIn 公开资料**，用外部信号补充自述；
3. **匿名化性别、年龄、种族等敏感属性**，并输出**可解释的排序理由**。

这三点对应筛选系统的三个真实痛点：匹配粒度、信息真实性、合规与可解释性。

### 2.3 对 LLM 筛选的效度审计

普林斯顿团队在 **AAAI 的 IASEAI 会议**上的工作最值得注意：构造「有已知优劣 ground truth」的简历数据集，测试多个 LLM 能否稳定选出更合格的候选人。

结论是负面的：**许多模型无法持续做出正确选择**；候选人资历相当时，模型**不会可靠「弃权」**；不同人群的选择率存在差异。

价值不在方法而在实证：给出了「LLM 筛选不可轻信」的依据。

### 2.4 多语言、扫描件与社交信号

有工作探索**手写 / 多语言简历的短列表**：Sentence-BERT 做语义匹配，OCR 处理扫描件，并引入 **GitHub 社交评分**作为辅助信号。解决的是真实场景的脏数据问题——简历不总是干净的 PDF。

### 2.5 对比表

| 路线 | 代表工作 | 方法 | 优势 | 局限 | 证据强度 |
|---|---|---|---|---|---|
| 传统 NLP + ML | IEEE 会议论文（TF-IDF+余弦+NER）；XGBoost 分类（77%）；排序综述（S1–S3） | TF-IDF、余弦、NER、XGBoost、协同过滤 | 确定性、可解释、成本低 | 语义泛化弱，依赖关键词与字段质量 | 二手整理，未核实 |
| LLM / 生成式 | ChatGPT-4o 公平筛选框架（IEEE，S4） | 技能加权 + 外部资料 + 敏感属性匿名化 + 可解释理由 | 语义理解强、可解释、可处理非结构化材料 | 成本高、稳定性待验证、合规风险 | 二手整理，未核实 |
| 效度审计 | 普林斯顿 IASEAI（AAAI）审计（S5） | 有 ground truth 的数据集，测多模型选择稳定性与人群差异 | 给出可靠性实证，方法可复用 | 结论负面：LLM 直接筛选不可轻信 | 二手整理，未核实 |
| 多语言/脏数据 | Sentence-BERT + OCR + GitHub 社交评分（S6） | 语义匹配 + 扫描件 OCR + 外部信号 | 覆盖真实场景脏数据 | 链路长，误差逐级累积 | 二手整理，未核实 |

## 三、开源工具

### 3.1 shortlist-ai

LLM 驱动的排序 CLI。后端可接 Claude，也可走本地 MLX（Qwen），兼顾效果与隐私。

流程设计值得借鉴：**先把 JD 解析成 requirements，再逐条判断每份简历是否满足，并输出证据引用**——不是给总分了事，而是回答「这条要求，简历里哪句话满足了」。另外提供 `stability` 命令，检测评分对措辞的敏感度，把「评估稳定性」做成了产品功能。

### 3.2 talent-lens（慧眼）

五维度量化评分工具，Python + LLM 辅助抽取。维度为**高校背景、大厂经历、职业稳定性、资深程度、学历**，支持 YAML 配置权重，CLI 与 API 双接口。

价值在于把「筛选偏好」显式化——权重写在配置里，可审、可改、可复盘。但这类维度天然带偏见（院校/大厂偏好），落地必须配合合规审查。

### 3.3 cvz

ATS 风格简历分析，spaCy + scikit-learn。权重明确：**关键词 50% + 语义 30% + 结构 20%**。

除单份分析外，支持 `compare` 多份横向对比，以及 **gap 分析**（指出简历缺失哪些 JD 要求）。对招聘方是筛选助手，对候选人是自查工具——同一逻辑服务两侧。

### 3.4 ai-recruitment-agent

批量筛选流水线，用 Google Gemini 1.5 Flash。读取 JD PDF，批量处理 CV 文件夹，打分后自动推送到 **Notion 数据库**，并按「邮箱 + 职位 ID」去重。

定位明确：不是分析工具，而是**把筛选塞进现有工作流**（招聘团队常用 Notion 管候选人）。去重逻辑说明它面向长期批量使用。

### 3.5 resume-screening-mcp

给 Agent 用的 **MCP 服务**（Node.js）。把 JD 解析、简历结构化、可信度检测、综合评分、排序、报告生成封装为 MCP 工具，供上层 agent 调用。

这类形态值得关注：筛选不再做成独立产品，而是作为「能力单元」被编排进更大的 agent 流程。

### 3.6 对比表

| 名称 | 链接 | 技术栈 | 核心功能 | 特色 | 成熟度 |
|---|---|---|---|---|---|
| shortlist-ai | 待补（S7） | Claude / 本地 MLX（Qwen） | JD 解析 → 逐条判定 → 证据引用；`stability` 稳定性检测 | 输出证据而非总分 | 待实测 |
| talent-lens（慧眼） | 待补（S8） | Python + LLM 抽取 | 五维度评分，YAML 配权重，CLI + API | 筛选偏好显式化、可审 | 待实测 |

## 四、机会与空白

- **可解释性正在成为标配**：shortlist-ai 的证据引用、ChatGPT-4o 框架的可解释理由，都在回答「凭什么排这个序」。
- **稳定性 / 效度审计几乎没有产品化**：学术侧已证明 LLM 筛选不稳定，工程侧只有 shortlist-ai 的 `stability` 命令沾边——明确空白。
- **偏见审计缺位**：talent-lens 的院校/大厂维度天然带偏见，未见配套的偏差检测或合规报告。
- **与生成侧共用内核**：两侧都需要「JD 解析 → 结构化匹配」，但目前没有工具同时服务两侧（cvz 最接近）。
