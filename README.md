# 简历自动生成与筛选：产品调查记录

本仓库记录 LLM 驱动的**简历生成**（候选人侧）与**简历筛选**（招聘方侧）两个方向的研究工作与开源工具调查，为产品决策提供参考。

- 调查范围：学术（arXiv、SIGIR、AAAI、IEEE 等）+ 工程（GitHub、PyPI、npm、Docker Hub）
- 截止日期：2026-10-25（筛选侧内容为 2026-10-25 追加）
- 证据强度：区分「已读原文/摘要」「仅看仓库文档」「二手整理未核实」，逐条登记在来源台账

---

## 一、核心结论

1. **生成侧有两条清晰的技术路线**：一条是「即时定制生成」——以 ResumeFlow（SIGIR 2024）为代表，拿单份简历 + JD 直接让 LLM 生成定制简历；另一条是「长期职业库检索增强」——以 Career-Aware Resume Tailoring（arXiv 2026 预印本）为代表，维护历史职业记录，用多源 RAG 组装简历。

2. **RAG 路线在低经验匹配场景下会退化**：Career-Aware 的试点评估显示，有相关过往经历的岗位 ATS 风格匹配分平均 +7.8，缺乏相关经验的岗位反而 −8.0。作者自述需要「置信度门控的检索」来解决。

3. **筛选侧比生成侧成熟得多**：筛选是招聘技术里研究最密集的方向之一，已形成传统 NLP+ML、LLM/生成式、效度审计三条路线，且多为正式 IEEE 会议论文而非预印本；开源工具的数量和可用性也高于生成侧。

4. **LLM 筛选的可靠性本身仍是开放问题**：普林斯顿团队在 AAAI IASEAI 的效度审计发现，多个 LLM 无法稳定选出更合格的候选人，在资历相当时不会可靠「弃权」，不同人群的选择率存在差异。这意味着「用 LLM 做筛选」不能直接当作可信结论使用。

5. **幻觉/偏见控制是两侧共同关注点**：生成侧靠结构化输入 + 确定性检查压制编造（Resume-Libre 的 31 项规则检查）、靠匿名化与可解释理由控制偏见（ChatGPT-4o 筛选框架）；学术侧则分别提出幻觉评估指标与 anti-hallucination guardrails。

## 二、研究工作：简历生成（候选人侧）

### 2.1 ResumeFlow（SIGIR 2024 Demo，arXiv:2402.06221）

代表「即时定制生成」路线。给定一份写得很详细的简历和目标岗位 JD，用现成的 GPT-4 或 Gemini 直接生成针对该岗位定制的简历，**不需要任何微调**，秒级出结果——这是它区别于同期微调方案的核心卖点。

除了生成流程，论文的主要贡献还包括一套针对该任务的评估指标：同时衡量生成内容与岗位的**对齐程度**，以及是否存在**幻觉**（编造候选人没有的经历或技能）。这套指标后来被同类工作引用为评估基线。

局限也很明确：它处理的是「单份简历 → 单个岗位」的一次性映射，不涉及跨岗位的长期职业库，也不做多源检索；简历的版本沉淀、历史管理不在讨论范围内。

### 2.2 Career-Aware Resume Tailoring（arXiv:2605.05257，预印本）

走的是另一条路：**长期职业库 + 多源检索增强**。它要求用户维护结构化的历史职业记录（存进向量数据库），面对新岗位时不只是改写当前简历，而是从整个职业库里检索、组装最相关的内容。

工程实现是一条 **12 节点的 LangGraph 流水线**，输入是历史简历 + 结构化职业记录 + JD，输出是针对该岗位重新组装的简历内容。

评估采用 ATS 风格的匹配分，在 **9 个 JD 上做单候选人试点**：有相关过往经历的岗位平均 **+7.8 分**，缺乏相关经验的岗位反而 **−8.0 分**，部分重叠的岗位约 **+2 分**。作者自己把低匹配场景的退化列为待解问题，提出需要「置信度门控的检索」（confidence-gated retrieval），并设置了 anti-hallucination guardrails。

硬伤同样明显：单一候选人、9 个 JD，样本量小，结论只能算方向性证据。

| 名称 | 来源/编号 | 技术路线 | 输入 | 输出 | 评估方式 | 关键发现 | 局限 | 证据强度 |
|---|---|---|---|---|---|---|---|---|
| ResumeFlow | SIGIR 2024 Demo；arXiv:2402.06221（S1/S2） | LLM 即时定制生成（GPT-4 / Gemini，无需微调） | 详细简历 + 目标职位描述 | 针对该职位定制化的简历 | 任务特定的对齐度与幻觉评估指标 | 秒级生成定制简历；完全 off-the-shelf 使用 | 未涉及长期职业库或多源检索 | 已读摘要 |

## 三、研究工作：简历筛选（招聘方侧）

> 说明：本节内容来自外部整理的调研摘要，**原论文标题与链接尚未补齐**（台账 S11–S16 标注为待补）。行文与结论按摘要转述，未经原文核对，引用前必须先补来源。

### 3.1 传统 NLP + 机器学习路线

这一路线用 TF-IDF、余弦相似度、命名实体识别（NER）或分类器完成简历与 JD 的匹配和排序，是筛选领域积累最厚的部分。

- 有 IEEE 会议论文用 **TF-IDF + 余弦相似度 + NER** 做简历排序，除性能外还讨论了偏见、透明度与数据隐私问题——说明「可解释与合规」从传统方法时期就是筛选研究的固定议题。
- 有工作用 **XGBoost 做职位分类（准确率 77%）**，配合自定义 NER 完成信息抽取，属于「先抽取结构化字段、再分类匹配」的典型两段式。
- 也有综述系统梳理了 TF-IDF、余弦相似度、NER 以及协同过滤等排序技术，可作为该路线的入门地图。

工程含义：这一类方法确定性好、可解释、成本低，至今仍是多数 ATS 产品的实际内核——生成侧那些「31 项规则检查」的工程做法，本质与之一脉相承。

### 3.2 LLM / 生成式 AI 路线

更新的工作开始把筛选交给大模型。一篇 IEEE 论文提出用 **ChatGPT-4o 构建「公平且可扩展」的筛选框架**，做法有三点值得注意：

1. 从 JD 提取技能并**加权**，而不是把所有关键词等权匹配；
2. 分析简历时**结合 GitHub / LinkedIn 公开资料**，用外部信号补充简历自述；
3. **匿名化性别、年龄、种族等敏感属性**，并输出**可解释的排序理由**。

这三点其实对应筛选系统的三个真实痛点：匹配粒度、信息真实性、合规与可解释性。

### 3.3 对 LLM 筛选的效度审计

普林斯顿团队在 **AAAI 的 IASEAI 会议**上的工作最值得注意：他们构造了一个「有已知优劣 ground truth」的简历数据集，测试多个 LLM 能否稳定选出更合格的候选人。

结论是负面的：**许多模型无法持续做出正确选择**；在候选人资历相当时，模型**不会可靠地「弃权」**；不同人群的选择率存在差异。

这项工作的价值不在方法，而在给出了「LLM 筛选不可轻信」的实证依据——任何把 LLM 排序结果直接当决策依据的产品设计，都必须先回答这类审计问题。

### 3.4 其他方向：多语言、扫描件与社交信号

还有工作探索**手写 / 多语言简历的短列表**：用 Sentence-BERT 做语义匹配，用 OCR 处理扫描件，并引入 **GitHub 社交评分**作为辅助信号。这条线解决的是真实招聘场景里的脏数据问题——简历不总是干净的 PDF。

| 路线 | 代表工作 | 方法 | 优势 | 局限 | 证据强度 |
|---|---|---|---|---|---|
| 传统 NLP + ML | IEEE 会议论文（TF-IDF + 余弦 + NER 排序）；XGBoost 职位分类（77%）；排序技术综述（S11–S13） | TF-IDF、余弦相似度、NER、XGBoost、协同过滤 | 确定性、可解释、成本低 | 语义泛化弱，依赖关键词与字段质量 | 二手整理，未核实原文 |

## 四、开源工具：候选人侧（简历生成）

### 4.1 Resume-Libre

功能最全的一个，基本是「把简历当产品做」的思路。技术栈 React 19 + FastAPI + Supabase，PDF 用 LaTeX（Tectonic）渲染，输出质量接近手工排版。功能覆盖 AI 生成、GitHub / LinkedIn 导入、按 JD 定制、版本控制、公开发布个人主页。

它最有参考价值的设计是 **ATS 检查走确定性路径**：31 项检查分 6 大类，不用 LLM 判断，而是规则化的硬检查；检查结果再注入提示词，触发一次「修复式重生成」。这个「先确定性检查、再让 LLM 修」的闭环，比单纯让模型自我评估靠谱得多。

许可证 AGPL-3.0，Docker Compose 自托管，提供无需 API Key 的 DEMO_MODE，适合先跑通再决定是否投入。

### 4.2 resume-builder-llm

一个结构清晰的 Next.js 全栈实现。技术栈 Next.js 15 + TypeScript + Vercel AI SDK，模型可选 OpenAI GPT-4o 或部署在 AWS Bedrock 上的 Llama 3 70B（后者适合有数据合规要求的场景）。

功能包括简历定制、求职信生成、内置 ATS 评分、实时 PDF 预览，核心概念是 **Master Profile（主档案）**：用户维护一份完整档案，AI 每次从中挑选与目标岗位相关的内容，而不是从零生成。这个思路和学术侧的「长期职业库」本质相同，但实现更轻。

本地 npm 运行，需要自备 API Key，许可证未在搜索结果中明确标注。

### 4.3 jobjob

一个 Python 命令行工具，定位是「一条命令搞定投递材料」。Python ≥3.12，底层用 Claude 模型，从 JD 生成定制简历、求职信和技能差距分析三件套。

工程上有个值得注意的细节：整个流程 **5 次 Claude 调用共享同一段缓存前缀**，把简历等固定上下文缓存在前面，显著降低 token 成本——这是生产化部署时绕不开的优化点。

MIT 许可证，pipx / pip 安装，附带一个本地浏览器面板；可选把结果上传 Google Drive。注意命令已变更：旧文档写 `jobjob apply`，新版实际是 `jobjob build`（版本 3.0.1）。

### 4.4 resi-builder

严格说不是一个产品，而是一个 **Python 库 / 构建块**。它提供 `build_resume_preview` 和 `build_resume_pdf` 两个接口，输入 JD 和用户历史数据，输出简历预览与 PDF。

抽象程度低、文档示例简单，适合作为自己系统的渲染层复用，不适合直接拿来给用户用。维护状态未确认。

### 4.5 StackResume

面向软件开发者的自托管方案，卖点是**数据不出本机**。核心是一条多代理 LangGraph 流水线，模型可接 OpenAI / Anthropic / Gemini，也可以完全走 Ollama 本地模型离线运行。

功能包括一句话生成简历、按 JD 定制（提供 0–100 的定制强度滑块，这个交互设计值得借鉴）、输出 PDF / Word / ODT、投递进度跟踪，以及对话式 UI。

GPL-3.0，Docker 单命令启动。自我描述为 "ATS-optimised"，但没有明确说明是否内置独立的 ATS 检查器——这点需要实测确认。

## 五、开源工具：招聘方侧（简历筛选）

> 说明：以下 5 个工具的**仓库/PyPI 链接尚未补齐**（台账 S17–S21），名称与功能来自外部整理，实测前需先确认项目是否存在、维护状态如何。

### 5.1 shortlist-ai

LLM 驱动的排序 CLI。后端可接 Claude，也可走本地 MLX（Qwen），兼顾效果与隐私。

流程设计值得借鉴：**先把 JD 解析成 requirements，再逐条判断每份简历是否满足，并输出证据引用**——不是给一个总分了事，而是回答「这条要求，简历里哪句话满足了」。另外提供 `stability` 命令，专门检测评分对措辞的敏感度（同一份简历换个说法分数会不会跳），这是把「评估稳定性」做成了产品功能。

### 5.2 talent-lens（慧眼）

五维度量化评分工具，Python + LLM 辅助抽取。五个维度是：**高校背景、大厂经历、职业稳定性、资深程度、学历**，支持 YAML 配置权重，提供 CLI 与 API 双接口。

它的价值不在技术，而在把「筛选偏好」显式化了——权重写在配置里，可审、可改、可复盘。但这类维度天然带偏见风险（院校/大厂偏好），落地时必须配合合规审查。

### 5.3 cvz

ATS 风格的简历分析工具，技术栈 spaCy + scikit-learn。打分权重明确：**关键词 50% + 语义 30% + 结构 20%**，三维加权。

除单份分析外，支持 `compare` 多份简历横向对比，以及 **gap 分析**（指出简历缺失哪些 JD 要求的能力）。对招聘方是筛选助手，对候选人则是自查工具——同一套逻辑服务两侧。

### 5.4 ai-recruitment-agent

批量筛选流水线，用 Google Gemini 1.5 Flash。读取 JD PDF，批量处理整个 CV 文件夹，打分后自动推送到 **Notion 数据库**，并按「邮箱 + 职位 ID」去重。

定位很明确：不是分析工具，而是**把筛选塞进现有工作流**（招聘团队常用 Notion 管候选人）。去重逻辑说明它考虑的是长期批量使用，而非一次性试用。

### 5.5 resume-screening-mcp

给 Agent 用的 **MCP 服务**（Node.js）。把 JD 解析、简历结构化、可信度检测、综合评分、排序、报告生成封装成 MCP 工具，供上层 agent 调用。

这类形态值得关注：筛选能力不再做成独立产品，而是作为「能力单元」被编排进更大的 agent 流程——和我们自己做论文润色流水线的思路同构。

## 六、机会与空白

**候选人侧（生成）**

- **跨职位长期职业库没有成熟产品**：学术侧有原型（Career-Aware），工程侧最近的只是「主档案」这种轻量近似实现。
- **低经验匹配场景的退化没有工程解法**：学术侧已暴露问题（−8.0），工程侧尚无对应机制。
- **版本管理与简历历史普遍薄弱**：多数工具聚焦单次生成，只有 Resume-Libre 做出了完整版本控制。
- **确定性检查 + LLM 修复的闭环值得复用**：Resume-Libre 的 31 项规则检查是当前最可借鉴的工程质量设计。

**招聘方侧（筛选）**

- **可解释性正在成为标配**：shortlist-ai 的证据引用、ChatGPT-4o 框架的可解释理由，都在回答「凭什么排这个序」。
- **稳定性/效度审计几乎没有产品化**：学术侧已证明 LLM 筛选不稳定（普林斯顿审计），工程侧只有 shortlist-ai 的 `stability` 命令沾边——这是明确的空白。
- **偏见审计缺位**：talent-lens 的院校/大厂维度天然带偏见，但未见配套的偏差检测或合规报告。

**两侧交叉**

- 生成侧与筛选侧共用同一套「JD 解析 → 结构化匹配」内核，但目前没有工具同时服务两侧（cvz 最接近）。
